# Other Datasets — Same Architecture, Different Problem
**Reference sheet for instructors and students**

**Core idea:** the four-container architecture (MLflow + Trainer + FastAPI + Streamlit) is completely reusable. The only things that change between projects are:
- The CSV file you put in `backend/data/processed/`
- The name of the target column you pass to `train.py`
- The labels you display in `frontend/app.py`
- Optionally, a few words in the UI description

Everything else — Docker Compose, both Dockerfiles, both `requirements*.txt`, `data_processing.py`, and the FastAPI route — stays exactly the same.

---

## What Never Changes

```
docker-compose.yml         ← identical across all projects
backend/Dockerfile         ← identical
backend/main.py            ← identical
backend/utils/__init__.py  ← identical (empty)
frontend/Dockerfile        ← identical
frontend/requirements-frontend.txt  ← identical
backend/requirements-backend.txt    ← identical
```

## What Always Changes

```
backend/data/processed/train.csv         ← your new dataset
backend/data/processed/train_col_types.json  ← regenerated by train.py automatically
backend/data/sample_test.csv             ← a sample of your new test data
backend/data/sample_test_labeled.csv     ← same sample with the true labels
```

## What You Tweak Slightly

In `docker-compose.yml`, the `trainer` service:

```yaml
command: ["python", "train.py", "--target", "YOUR_TARGET_COLUMN_NAME"]
```

In `frontend/app.py`, two constants and the description text:

```python
TARGET_COL = 'YOUR_TARGET_COLUMN_NAME'
LABELS     = {1: 'Your label for class 1', 0: 'Your label for class 0'}
```

That's it. The rest is identical.

### Project 1 — Bank Marketing: Will the Client Subscribe to a Term Deposit?

**Domain:** Retail banking

**Business question:** A bank runs phone marketing campaigns. Which clients are most likely to subscribe to a term deposit after being called? Targeting only likely subscribers reduces wasted calls and improves conversion rates.

**Dataset:** [UCI Bank Marketing Dataset](https://archive.ics.uci.edu/dataset/222/bank+marketing)

**Kaggle link:** [https://www.kaggle.com/datasets/janiobachmann/bank-marketing-dataset](https://www.kaggle.com/datasets/janiobachmann/bank-marketing-dataset)

**Size:** ~45 000 rows, 17 columns

**Target column:** `y` (values: `yes` / `no` — convert to 1 / 0 during preprocessing)

**Key input features:**

| Column | Meaning |
|---|---|
| `age` | Client age |
| `job` | Type of job (admin, blue-collar, entrepreneur, ...) |
| `marital` | Marital status (married, single, divorced) |
| `education` | Education level |
| `balance` | Average yearly account balance in euros |
| `housing` | Has a housing loan? (yes/no) |
| `loan` | Has a personal loan? (yes/no) |
| `contact` | Contact communication type (cellular, telephone) |
| `duration` | Last contact duration in seconds |
| `campaign` | Number of contacts during this campaign |
| `pdays` | Days since last contact from a previous campaign |
| `poutcome` | Outcome of the previous marketing campaign |

**Preprocessing steps (what you do in a notebook before handing train.csv to the trainer):**
1. Encode `y`: replace `yes` → 1, `no` → 0.
2. One-hot encode all categorical columns (`job`, `marital`, `education`, `contact`, `poutcome`).
3. Drop `duration` if you want a realistic model (duration is only known after the call — it leaks the outcome in training but is unknown at prediction time).
4. Split into `train.csv` and `sample_test.csv`.

**Change in `docker-compose.yml`:**

```yaml
command: ["python", "train.py", "--target", "y"]
environment:
  MODEL_NAME: bank-marketing-automl
```

**Change in `frontend/app.py`:**

```python
TARGET_COL = 'y'
LABELS     = {1: 'Will subscribe to term deposit', 0: 'Will not subscribe'}
```

**What the app does:** the user uploads a CSV of potential clients. The app predicts which ones to call first in the next marketing campaign.

### Project 3 — Credit Card Fraud Detection: Is This Transaction Fraudulent?

**Domain:** Financial services / fraud detection

**Business question:** A credit card company processes millions of transactions per day. The fraud team needs to identify which transactions are fraudulent in near-real-time to block them before money is lost.

**Dataset:** [Credit Card Fraud Detection (Kaggle)](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud)

**Size:** ~284 807 rows, 31 columns. **Extremely imbalanced:** only 0.17% of transactions are fraud.

**Target column:** `Class` (values: 0 = legitimate, 1 = fraud)

**Key input features:**

| Column | Meaning |
|---|---|
| `V1` to `V28` | PCA-transformed features (anonymized for privacy) |
| `Amount` | Transaction amount in euros |
| `Time` | Seconds elapsed since first transaction in the dataset |

**Note:** the features V1–V28 are already numerical. No one-hot encoding needed. But you must handle the severe class imbalance. H2O AutoML's `balance_classes=True` parameter (already set in `train.py`) handles this automatically.

**Preprocessing steps:**
1. Standardize `Amount` with a StandardScaler (or MinMaxScaler).
2. Drop the `Time` column (it represents position in the dataset, not a real time feature).
3. The dataset is ready — no categorical columns to encode.

**Change in `docker-compose.yml`:**

```yaml
command: ["python", "train.py", "--target", "Class"]
environment:
  MODEL_NAME: fraud-detection-automl
  # Use more data here — fraud detection benefits from large samples
  AUTOML_SAMPLE_FRAC: "0.5"
  AUTOML_MAX_MODELS: "8"
  AUTOML_MAX_RUNTIME_SECS: "300"
```

**Change in `frontend/app.py`:**

```python
TARGET_COL = 'Class'
LABELS     = {1: 'Fraudulent transaction', 0: 'Legitimate transaction'}
```

**What the app does:** the fraud team uploads a batch of transactions. The app immediately flags which ones are likely fraudulent. The compliance team reviews only the flagged transactions instead of the entire batch.

**Important teaching point:** with an imbalanced dataset, **accuracy is a misleading metric**. A model that always predicts "legitimate" achieves 99.83% accuracy but catches zero fraud. For this project, **recall on the fraud class** is the metric that matters — you want to catch as many fraudulent transactions as possible, even at the cost of some false alarms.

### Project 4 — Hospital Readmission: Will This Patient Be Readmitted Within 30 Days?

**Domain:** Healthcare

**Business question:** A hospital wants to identify patients at high risk of being readmitted within 30 days after discharge. These patients can receive additional follow-up care (a nurse call, a follow-up appointment, medication reminders) to prevent the readmission.

**Dataset:** [Diabetes 130-US Hospitals 1999-2008 (UCI / Kaggle)](https://www.kaggle.com/datasets/brandao/diabetes)

**Size:** ~101 766 rows, 50 columns

**Target column:** `readmitted` (values: `<30` = readmitted in under 30 days → 1, `>30` or `NO` → 0)

**Key input features:**

| Column | Meaning |
|---|---|
| `age` | Age bracket (e.g., [60-70)) |
| `time_in_hospital` | Number of days spent in the hospital |
| `num_lab_procedures` | Number of lab tests performed |
| `num_procedures` | Number of medical procedures |
| `num_medications` | Number of medications prescribed |
| `number_outpatient` | Number of outpatient visits in the prior year |
| `number_emergency` | Number of emergency visits in the prior year |
| `number_inpatient` | Number of inpatient visits in the prior year |
| `number_diagnoses` | Number of diagnoses entered |
| `A1Cresult` | A1C test result (HbA1c — measure of long-term blood sugar control) |
| `insulin` | Was insulin prescribed? (Down, Steady, Up, No) |
| `change` | Was the diabetes medication changed? (Ch, No) |
| `diabetesMed` | Was any diabetes medication prescribed? (Yes, No) |

**Preprocessing steps:**
1. Create binary target: `readmitted == '<30'` → 1, else → 0.
2. Drop identifier columns (`encounter_id`, `patient_nbr`).
3. Replace `?` with NaN in categorical columns — H2O handles NaN natively.
4. One-hot encode: `race`, `gender`, `age`, `admission_type_id`, `discharge_disposition_id`, `admission_source_id`, `A1Cresult`, `insulin`, `change`, `diabetesMed`.

**Change in `docker-compose.yml`:**

```yaml
command: ["python", "train.py", "--target", "readmitted"]
environment:
  MODEL_NAME: readmission-automl
```

**Change in `frontend/app.py`:**

```python
TARGET_COL = 'readmitted'
LABELS     = {1: 'High readmission risk — follow up required', 0: 'Low readmission risk'}
```

**What the app does:** clinical staff upload a discharge list for the day. The app flags patients at high risk of returning within 30 days. Nurses prioritize follow-up calls for those patients.

### Project 7 — Loan Default: Will This Borrower Default on Their Loan?

**Domain:** Lending / fintech

**Business question:** A lending company needs to decide which loan applications to approve. They want a model that predicts the probability that an applicant will default (fail to repay) based on their application data.

**Dataset:** [Give Me Some Credit (Kaggle)](https://www.kaggle.com/competitions/GiveMeSomeCredit/data)

**Size:** ~150 000 rows, 11 columns

**Target column:** `SeriousDlqin2yrs` (1 = the borrower experienced 90+ days delinquency in the next 2 years, 0 = they did not)

**Key input features:**

| Column | Meaning |
|---|---|
| `RevolvingUtilizationOfUnsecuredLines` | Total balance on credit cards / credit limit (ratio) |
| `age` | Borrower's age in years |
| `NumberOfTime30-59DaysPastDueNotWorse` | Number of times 30–59 days past due in last 2 years |
| `DebtRatio` | Monthly debt payments / monthly income |
| `MonthlyIncome` | Monthly income in USD |
| `NumberOfOpenCreditLinesAndLoans` | Number of open credit lines and loans |
| `NumberOfTimes90DaysLate` | Number of times 90+ days past due |
| `NumberRealEstateLoansOrLines` | Number of mortgage and real estate loans |
| `NumberOfTime60-89DaysPastDueNotWorse` | Number of times 60–89 days past due in last 2 years |
| `NumberOfDependents` | Number of dependents in family |

**Preprocessing steps:**
1. `SeriousDlqin2yrs` is already 0/1 — no encoding needed.
2. Handle missing values: `MonthlyIncome` (~20% missing) and `NumberOfDependents` (~3% missing). H2O AutoML handles NaN internally, but filling with median is safer.
3. Clip extreme outliers: `RevolvingUtilizationOfUnsecuredLines` > 1 (some values are 50 000+), `DebtRatio` > 1 (cap at 1.0 or drop outliers).
4. No categorical columns — everything is already numerical.

**Change in `docker-compose.yml`:**

```yaml
command: ["python", "train.py", "--target", "SeriousDlqin2yrs"]
environment:
  MODEL_NAME: loan-default-automl
  AUTOML_SAMPLE_FRAC: "0.4"
  AUTOML_MAX_MODELS: "8"
  AUTOML_MAX_RUNTIME_SECS: "300"
```

**Change in `frontend/app.py`:**

```python
TARGET_COL = 'SeriousDlqin2yrs'
LABELS     = {1: 'High default risk — loan denied or higher rate', 0: 'Low default risk — loan approved'}
```

**What the app does:** the credit team uploads a CSV of loan applications. The app instantly scores each applicant. Applications flagged as high risk are reviewed more carefully or offered a smaller loan amount at a higher interest rate.

### Project 8 — Student Performance: Will This Student Pass or Fail?

**Domain:** Education / EdTech

**Business question:** A school or online learning platform wants to identify students who are at risk of failing before the end of the term. Early identification allows counselors and teachers to intervene — extra tutoring, check-in meetings, schedule adjustments — before the student falls too far behind.

**Dataset:** [Student Performance Dataset (UCI)](https://archive.ics.uci.edu/dataset/320/student+performance) / [Kaggle mirror](https://www.kaggle.com/datasets/devansodariya/student-performance-data)

**Size:** ~395 rows for Math, ~649 rows for Portuguese (small — good for rapid lab sessions)

**Target column:** You create it from `G3` (final grade): `pass = 1 if G3 >= 10 else 0`

**Key input features:**

| Column | Meaning |
|---|---|
| `age` | Student age (15–22) |
| `school` | School attended (GP or MS) |
| `sex` | M or F |
| `address` | Urban (U) or Rural (R) |
| `famsize` | Family size (LE3 = ≤3 members, GT3 = >3 members) |
| `Pstatus` | Parents' cohabitation status (Together or Apart) |
| `Medu` | Mother's education level (0–4) |
| `Fedu` | Father's education level (0–4) |
| `Mjob` | Mother's job (teacher, health, services, at_home, other) |
| `Fjob` | Father's job |
| `reason` | Why this school was chosen (home, reputation, course, other) |
| `studytime` | Weekly study time (1–4 scale) |
| `failures` | Number of past class failures (0–4) |
| `schoolsup` | Extra educational support from school? (yes/no) |
| `famsup` | Family educational support? (yes/no) |
| `paid` | Extra paid classes? (yes/no) |
| `activities` | Participates in extracurricular activities? (yes/no) |
| `absences` | Number of school absences |
| `G1` | First period grade (0–20) |
| `G2` | Second period grade (0–20) |

**Preprocessing steps:**
1. Create the target: `pass = (G3 >= 10).astype(int)`.
2. Drop `G1`, `G2`, and `G3` if you want a realistic early-warning model (the grades leak the outcome). Keep only pre-term features. Or keep `G1` and `G2` if you want a mid-term warning model.
3. Encode binary yes/no columns: `schoolsup`, `famsup`, `paid`, `activities`, `nursery`, `higher`, `internet`, `romantic` → 1/0.
4. One-hot encode: `school`, `sex`, `address`, `famsize`, `Pstatus`, `Mjob`, `Fjob`, `reason`, `guardian`.

**Change in `docker-compose.yml`:**

```yaml
command: ["python", "train.py", "--target", "pass"]
environment:
  MODEL_NAME: student-pass-automl
  AUTOML_SAMPLE_FRAC: "1.0"
  AUTOML_MAX_MODELS: "10"
  AUTOML_MAX_RUNTIME_SECS: "180"
```

**Change in `frontend/app.py`:**

```python
TARGET_COL = 'pass'
LABELS     = {1: 'Likely to pass — no intervention needed', 0: 'At risk of failing — schedule support'}
```

**What the app does:** a counselor uploads a CSV with all enrolled students' demographic and behavioral data at mid-term. The app flags which students are at risk of failing. The school schedules tutoring sessions or counseling meetings for those students before the final exam.

## The Three Files That Change Every Project

### 1. In `docker-compose.yml` — trainer section

```yaml
trainer:
  command: ["python", "train.py", "--target", "YOUR_TARGET_COLUMN"]
  environment:
    MODEL_NAME: your-project-automl
    AUTOML_MAX_MODELS: "10"        # more models = better accuracy, slower training
    AUTOML_MAX_RUNTIME_SECS: "300" # increase if dataset is large
    AUTOML_SAMPLE_FRAC: "1.0"      # reduce to 0.2 or 0.5 for large datasets in labs
```

### 2. In `frontend/app.py` — two lines at the top

```python
TARGET_COL = 'YOUR_TARGET_COLUMN'
LABELS     = {1: 'Your positive class label', 0: 'Your negative class label'}
```

### 3. Your preprocessed data files

```
backend/data/processed/train.csv            ← your project's training data
backend/data/sample_test.csv                ← a small sample for testing (no labels)
backend/data/sample_test_labeled.csv        ← same sample with labels (for evaluation)
```

The file `train_col_types.json` is **generated automatically** by `train.py` — you never write it by hand.
